## Context

当前 Marivo 项目主要通过命令行和 AI 编码助手使用，缺乏 Web 界面。需要构建一个 Web 系统来降低使用门槛，让用户能够方便地发现、管理和运行 Marivo 项目。

参考 OpenDeepWiki 的设计理念——用户只需输入仓库地址或上传 ZIP 包即可加载项目，并通过对话式交互进行分析。本系统借鉴此模式，为 Marivo 项目提供类似的一站式 Web 体验。

系统需要：
- 集成 GitHub/GitLab API 实现项目的拉取和推送
- 支持 ZIP 压缩包上传和 Marivo 项目验证
- 提供项目浏览和管理功能
- 提供交互式 Q&A 对话界面，支持多轮提问分析
- 支持 Marivo 分析任务的执行和结果展示
- 确保安全性和性能

## Goals / Non-Goals

**Goals:**
- 构建完整的 Web 应用，支持项目浏览、搜索、创建和管理
- 集成 GitHub/GitLab OAuth 实现用户认证和项目访问
- 支持 ZIP 压缩包上传并自动验证 Marivo 项目结构
- 提供交互式 Q&A 对话界面，支持多轮自然语言提问
- 提供安全的容器化环境运行 Marivo 分析任务
- 展示分析结果的可视化界面，支持流式响应
- 支持项目同步和版本管理

**Non-Goals:**
- 不构建 Marivo 核心框架（这是 Python 库）
- 不替代现有的 AI 编码助手工作流
- 不提供 Marivo 的完整文档站点功能
- 不在第一版中支持多租户隔离

## Decisions

### 决策 1: 技术栈选择

**选择:** 前端使用 React + TypeScript + Tailwind CSS，后端使用 Node.js + Express，数据库使用 PostgreSQL。

**理由:**
- React 生态成熟，组件复用性好
- TypeScript 提供类型安全，减少运行时错误
- Tailwind CSS 加速 UI 开发
- Node.js 与前端技术栈一致，降低维护成本
- PostgreSQL 适合存储结构化数据和关系

**替代方案:**
- Next.js: 更好的 SEO 和 SSR，但增加了复杂度
- Python FastAPI: 与 Marivo 技术栈一致，但前后端技术栈分离
- SQLite: 简单但扩展性差

### 决策 2: GitHub/GitLab 集成方式

**选择:** 支持 GitHub OAuth 2.0 和 GitLab OAuth 2.0 进行用户认证，使用对应平台的 REST API 进行项目操作。

**理由:**
- OAuth 是标准的认证方式，用户体验好
- 双平台支持覆盖更多用户场景
- 统一的项目管理接口

**替代方案:**
- 仅支持 GitHub: 开发成本低但限制了用户选择
- SSH key: 安全性高但不适合 Web 场景

### 决策 3: 交互式 Q&A 对话架构

**选择:** 使用 SSE (Server-Sent Events) 实现流式对话响应，集成 AI 模型（如 Claude API / OpenAI）进行自然语言理解和分析。

**理由:**
- SSE 比 WebSocket 更轻量，适合单向流式文本传输
- 与现有 AI 模型 API 的流式接口天然兼容
- 前端实现简单，浏览器原生支持 EventSource
- 保持对话上下文以实现多轮交互

**替代方案:**
- WebSocket: 双向通信能力强，但实现复杂、资源开销大
- 短轮询: 实现简单但实时性差，不适合对话场景

### 决策 4: ZIP 上传处理方式

**选择:** 后端使用 `adm-zip` 或 `unzip` 库处理 ZIP 上传，上传后自动解压并验证 Marivo 项目结构。

**理由:**
- 服务端处理确保安全性（扫描恶意文件）
- 统一的验证流程（检查 marivo.toml、models/ 等）
- 支持大文件流式处理

**限制:**
- 单文件大小限制 100MB
- 仅支持 ZIP 格式
- 上传后存储到临时目录，用户可选择保存到仓库

### 决策 5: 分析任务执行方式

**选择:** 使用 Docker 容器隔离执行 Marivo 分析任务，通过 SSE/WebSocket 实时推送进度。

**理由:**
- Docker 提供安全的隔离环境
- 避免宿主机的依赖冲突
- SSE 提供实时反馈
- 支持并发执行多个任务

**替代方案:**
- 直接在宿主机执行: 性能更好但有安全风险
- 异步队列: 需要额外的基础设施

### 决策 6: 项目存储方式

**选择:** 项目存储在平台本地文件系统，可选择同步到 GitHub/GitLab 仓库。平台存储项目元数据、对话历史和分析记录。

**理由:**
- ZIP 上传的项目需要本地存储
- 用户可选择将项目推送到自己的仓库
- 对话历史和分析记录与项目关联存储

**替代方案:**
- 仅 GitHub 托管: 不支持 ZIP 上传和 GitLab
- 纯云端存储: 成本高且复杂

## Risks / Trade-offs

1. **GitHub/GitLab API 速率限制** → 实现缓存和分页策略，使用 OAuth App 提高限额
2. **容器执行安全** → 使用 read-only 文件系统、限制资源、网络隔离
3. **大项目克隆/ZIP 上传性能** → 支持 shallow clone、增量更新、后台任务
4. **用户认证安全** → 使用 HTTPS、token 加密存储、定期轮换
5. **AI 对话延迟** → 使用流式 SSE 响应，前端展示打字机效果，后台异步处理
6. **ZIP 文件安全** → 扫描恶意文件、限制解压路径、防止 zip bomb

## Architecture Overview

参考 OpenDeepWiki 的架构设计，系统分为以下核心模块：

```
用户浏览器 (React + TypeScript)
    │
    ├── 项目浏览页 ── 项目列表、搜索、筛选
    ├── 项目详情页 ── 文件树、README、配置预览
    ├── 对话分析页 ── Q&A 聊天界面、流式响应
    └── 分析结果页 ── 图表、指标、导出
    │
    ▼
API 网关 (Node.js + Express)
    │
    ├── 项目服务 ── 项目管理、搜索、验证
    ├── 集成服务 ── GitHub/GitLab API、ZIP 解析
    ├── 对话服务 ── AI 对话、上下文管理、SSE 流式
    └── 分析服务 ── Docker 任务编排、WebSocket 实时
    │
    ▼
数据层 (PostgreSQL)
    ├── 项目元数据
    ├── 用户信息
    ├── 对话历史
    └── 分析记录
```

## Migration Plan

1. **Phase 1**: 搭建基础框架，实现项目浏览、GitHub/GitLab 登录和 ZIP 上传
2. **Phase 2**: 实现交互式 Q&A 对话界面、AI 分析集成和流式响应
3. **Phase 3**: 添加可视化图表、分析结果展示和高级功能（会话管理、导出）

**回滚策略:** 每个 phase 独立部署，有问题可以快速回退到上一个稳定版本。
